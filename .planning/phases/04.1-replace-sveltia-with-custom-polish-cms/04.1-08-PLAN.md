<objective>
Give staff full control of the documents drawer: a grouped Polish list, adding a document with its file, replacing that file, editing the metadata and deleting both halves together.

Purpose: documents are the second collection ROADMAP SC3 names, and they are the only content in the phase whose payload is an arbitrary binary rather than a re-encoded image. That makes the free-tier CPU budget the deciding constraint, and it forces one explicit deviation from the UI-SPEC surface table that this plan records rather than smuggles.

Output: a document validator proven against the existing reader, a minimal file island that encodes in the browser, four screens, and a proven one-commit add.
</objective>

<planner_decisions>
- **P-22 (a recorded deviation from the UI-SPEC surface table, and the reason for it):** the UI-SPEC route table marks the dokumenty screens as needing no JavaScript, and Component Contract 8 calls the photo island the only hydrated component. That is not achievable for the file field. A document may be up to ten megabytes, and base64-encoding ten megabytes inside the request would consume many times the roughly ten millisecond free-plan CPU budget; the whole reason D-12 moved image encoding into the browser applies here with more force, not less. The file field therefore uses a MINIMAL island that reads the chosen file into a data URL and writes it into a hidden field, exactly the mechanism the photo island already uses, with no decoding, no canvas and no image work. Everything else on the document screens, the name, the category, the version date, the BIP link and the placeholder flag, works with JavaScript disabled, and an existing document's metadata can be edited and saved without JavaScript; only ATTACHING a file needs it. The screens carry the same honest no-script panel the photo fieldset carries, worded for a file. This deviation is recorded here, in the component's header comment and in the SUMMARY so the phase's SC2 and D-17 review treats it as a decision rather than a defect. It is the same class of tradeoff as the accepted native-file-input locale exception.
- **P-23 (file naming and identity):** a document's identity is the slug of its name. The JSON is that slug with a JSON extension under the content directory, the file is that slug with the uploaded file's lowercased extension under the static documents directory, and the `plik` field is the canonical public path built from it. A create whose slug already exists is refused with the collision message Plan 06 added to the copy module, rather than overwriting. Replacing the file of an existing document keeps the slug and therefore keeps the public path, unless the extension changes, in which case the old file is deleted in the same commit.
- **P-24 (dormant category):** the RODO category stays in the select with its UI-SPEC hint saying it will be enabled later. It is dormant on the public page by a Phase 2 decision, and quietly dropping it from the panel would strand any entry that already uses it.
</planner_decisions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser file picker to hidden field | the data URL is entirely client controlled and untrusted on arrival |
| hidden field to static directory | the only path by which an arbitrary binary enters the repository and becomes publicly downloadable |
| document name to file path | the only human-supplied value that shapes a filesystem path |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-04.1-31 | Tampering | path traversal through the document path | high | mitigate | The path is built from a strict character-class slug and an extension drawn from an allow-list, never from the submitted filename; the delete path is derived from the stored entry, not from the route parameter; the existing reader independently refuses a path without the canonical prefix or containing traversal segments. Enforced by behavior 4 and 6 unit cases. |
| T-04.1-32 | Tampering | an executable or script uploaded and served from the public site | high | mitigate | A strict media-type allow-list limited to PDF, DOC and DOCX, plus an extension allow-list applied to the written path, so the served content type cannot be chosen by the uploader. |
