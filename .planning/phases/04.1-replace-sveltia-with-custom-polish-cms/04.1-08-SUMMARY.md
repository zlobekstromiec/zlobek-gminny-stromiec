## The One Discovery That Reshaped This Plan

**The panel cannot import `src/lib/server/dokumenty.ts` at all, and the reason is not stylistic.** That module imports `node:fs` and stats every document on disk to compute its size (D-14). That is correct for the public pages, which are PRERENDERED at build time in Node. The panel is not prerendered: its routes are the Cloudflare Worker, `wrangler.jsonc` enables only `nodejs_als`, and a Worker has no filesystem. Any admin route importing that reader would have put `node:fs` into the Worker bundle.

Three things follow, and all three are improvements rather than compromises:

1. **The category union moved to `src/lib/kategorie-dokumentow.ts`** and the public reader imports it back and re-exports the type. Exactly the arrangement `src/lib/daty.ts` got in Plan 06 and `src/lib/zdjecia.ts` in Plan 07, now for the third time and for a harder reason. One declaration, four importers: the validator, the panel reader, the category select and the public grouper.
2. **The panel has its own reader**, `src/lib/server/admin/dokumenty.ts`, with no `node:fs` and no filtering. That turned out to be what the plan asked for anyway: `withMeta` SKIPS an entry whose file is missing and `groupDokumenty` OMITS an empty category, and the panel must do neither.
3. **The panel row shows type and version date, not size.** See the UI-SPEC section below: this is where the plan's own text and the LOCKED contract disagreed, and the contract was right for a reason neither document stated.

## Where The Plan And The LOCKED UI-SPEC Disagreed

**The plan's Task 2 says the row meta follows „the public documents convention of type, size and dotted version date". UI-SPEC Component Contract 4 says `PDF · wersja z 02.04.2026`. The UI-SPEC wins, and it wins on a technical fact rather than on precedence.** A size can only come from two places: a `stat` of the file, which the Worker cannot do, or a number stored in the entry, which is precisely what D-14 forbids because a stored size cannot be corrected when a file is replaced. `metaDokumentu(typ, wersja)` therefore renders exactly the contract's two-part line, the reason is written into the function's own doc comment, and the same reasoning decides what the edit screen shows about the currently attached file: its NAME and its type, not its size.

## What Was Built

**The server half, and again the point is what it does not do.** `base64ZDataUrlDokumentu` checks the type, then the length against `MAKS_PLIKU_BASE64`, and only then runs an anchored pattern admitting exactly three media types and a payload charset with nothing in it that could break out of the request body `commit.ts` assembles by concatenation. It returns a substring and a table lookup. The grep for the four byte-work APIs returns **0**. Two refinements over the photo module it is modelled on:

- **The cap is DERIVED** (`Math.ceil(MAKS_PLIKU_DOKUMENTU / 3) * 4`), so the ten megabytes the hint promises, the ten megabytes the refusal names and the character count the server enforces are one number in one place.
- **The pattern is BUILT from the allow-list** rather than written beside it, so a type added to `src/lib/pliki.ts` cannot be offered by the control and refused by the server.

**One match yields both the payload and the extension.** The plan describes an extraction returning the payload and a separate path builder taking an extension. Two functions each running the pattern would scan a fourteen megabyte string twice for one answer, which is the exact cost this module exists to avoid, so the extraction returns `{ base64, rozszerzenie }` and the payload is still handed on character for character unchanged (asserted directly).

**The path is the only place a typed value could reach a file, and nothing typed reaches it.** The slug comes from `slugAscii`, whose output is either empty or lowercase ASCII letters, digits and single hyphens; the extension comes from the allow-list table keyed by the accepted media type, never from the submitted filename. Seven hostile names are driven through the join and asserted to produce no traversal segment, no separator, no percent encoding and exactly one path segment under the documents directory. `sciezkaZPubliczej` closes the reverse direction for deletions: it accepts only a value carrying the canonical prefix and no separator, so a deletion removes the file the ENTRY names.

**A name that slugs to nothing is refused.** „***" would otherwise produce a file called only its own extension, which no editor could ever find again. Refused with „Podaj nazwę dokumentu.", keyed to the name field.

**The list shows more than the website does, deliberately and in two directions.** Every category renders its heading, including the dormant RODO drawer, each empty one carrying the one-line note; and an entry whose file is missing is still listed, because that is precisely the entry somebody has to open and fix. Both are asserted in the browser.

**The island is smaller than the photo island on purpose.** A native file input, a real visible label, a polite status line, a hidden field, the chosen file's name and size as text, and one button that clears the pending selection and returns focus to the input. It does not decode, does not draw on an off-screen surface, does not crop, does not re-encode and shows no preview. The motion grep returns **0**, so there is nothing to neutralise under a reduced-motion preference, and the file says so.

**The type comes from the browser, never from the filename.** Inferring `application/pdf` from an `.pdf` extension would hand the choice of media type to the person choosing the file, which is threat T-04.1-32 exactly. A file whose operating system does not report a type is therefore refused with a Polish instruction rather than quietly relabelled. That is the safe direction to be wrong in, and it is written into the handler.

**Both halves travel together in every direction.** A create builds ONE file list (JSON first, then the binary) and makes ONE call to the orchestrator. An edit with no new file commits only the JSON and keeps the file the document has. An edit with a new file of the same type overwrites in place and lists NO deletion, because one commit cannot both write and remove one path (the P-21 lesson from Plan 07, applied before it could bite). An edit with a new file of a different type writes the new path and removes the old one in the same commit. A deletion removes the entry and the file in one call.
