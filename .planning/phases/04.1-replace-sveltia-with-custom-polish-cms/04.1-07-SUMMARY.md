**A photo chosen from a phone or a computer is now decoded, centre cropped to 16:9, shrunk and re-encoded entirely in the browser, previewed as the exact bytes that will publish, and committed together with its entry as ONE commit, while the server that accepts it never reads, decodes or re-encodes a single byte and refuses the save outright if the picture arrives without a description, with scripting on or off.**

## What Was Built

**The server half, and the point of it is what it does not do.** `base64ZDataUrl` checks the type, then the length against `MAKS_BASE64`, and only then runs an anchored pattern that admits exactly three image types and a payload charset with nothing in it that could break out of the request body `commit.ts` assembles by concatenation. It returns a substring. There is no encoder, no decoder, no byte array and no allocation anywhere in the file, and the acceptance grep for those four names returns 0. `zaDuzeZdjecie` sits beside the cap so „this photo is too large" and „this is not a photo" cannot drift into one message.

**A filename that cannot silently fail.** `nazwaOkladki` is the entry's own filename stem with a lowercase `.jpg`, which makes the two files of one entry differ only in their extension and, more importantly, guarantees the name is inside the glob the three public consumers resolve covers through. Pitfall 4 is the failure this prevents: an upper-case extension or an avif would commit successfully, build successfully, warn about nothing, and render the decorative tint instead of the photograph forever.

**The one value in this submission that could reach a written path.** The edit screen carries the entry's current cover back in a hidden field so a save that changes only the title keeps the picture, and that value is client controlled. `bezpiecznaNazwaOkladki` admits it from an ALLOWLIST, never cleans it up: lowercase letters, digits, single hyphens, one dot, one of four extensions. Nineteen hostile values are driven through it in the unit suite, including both traversal shapes, an embedded separator, a percent-encoded separator, a double extension and an upper-case one, each paired with positive controls that include both real files in the uploads directory.

**The island, which is deliberately the most boring component in the phase.** A native file input with a real visible label, a polite status line, a preview box that reserves the ratio before anything paints, two buttons that commit nothing, and the required description field. On selection it decodes with the orientation option passed explicitly, crops from the centre, scales the longest edge to at most 1600 pixels, encodes as JPEG at 0.82 and writes a data URL into a hidden field. **Nothing in the file moves**: the grep for motion returns 0, there is no spinner and no progress bar, and the status sentence is the progress indicator. That is why it needs no reduced-motion guard, and the file says so.

**The two-file commit.** Both editor actions build one file list and hand it to ONE call to the save orchestrator, so the JSON and its cover enter one tree, one commit and one Cloudflare build. There is no window in which a post is live on the żłobek's website without its picture, which is D-07 and the reason the Contents API was rejected in research.

## The Preview Is The Bytes, Proven Rather Than Claimed

The browser case reads the `src` of the preview element and the value of the hidden field and asserts they are the SAME STRING. Not both-look-like-a-data-URL: identical. That is what makes „tak zdjęcie pojawi się na stronie" a true sentence rather than a hopeful one, and it is the assertion that would catch a future refactor that rendered the original file in the preview while sending the re-encoded one.

## What The Plan Asked For And What Was Built Instead

**1. The validator does not return the target basename.** The plan says it should return „the base64 payload and the target basename alongside the validated entry". It returns the payload and a removal flag; the basename is composed by the route. The reason is P-19 itself: the cover is named after the entry's own filename stem, and on a CREATE that stem is derived from the title and date the validator is in the middle of validating. A validator that produced the name would have to run the slug generator on values it had not finished accepting. `zOkladka` in the same module folds the name and description into the stored object rebuilt KEY BY KEY, so the two optional photo keys stay between `tresc` and `placeholder` where both seed files put them, and the route never assigns onto a validated object.

**2. The keyboard order in the browser case follows the UI-SPEC, not the plan's sentence.** The plan describes tabbing „to the alt field, tab to both buttons". Component Contract 8 fixes the DOM order as file input, status, preview, action buttons, alt field, and the LOCKED contract wins. The case walks the real order: file input, „Wybierz inne zdjęcie", „Usuń zdjęcie", description.

**3. The cover is not deleted merely because no other aktualność points at it.** The plan's rule for the delete action is „no OTHER entry references that basename". Applied literally it would have deleted `sala-zabaw.jpg` when the seeded entry is removed, and the o nas page renders that exact file: `src/lib/content/o-nas.json` lists it under `obiekt_zdjecia`. `okladkaDoUsuniecia` therefore adds a stricter first condition: the name must be the one THIS entry's stem generates. A cover the panel created belongs to its entry and to nothing else; a hand-set name may be shared. An unreferenced leftover costs a few kilobytes in a directory listing, a missing shared file breaks a public page.

## Hydration Of The No-Script Notice, Checked Rather Than Assumed

A browser with scripting ENABLED parses the contents of a `<noscript>` element as plain text and never builds a tree from it, which is exactly the shape of markup a hydration mismatch comes from: the component expects a div and finds a text node. Rather than guess, the Svelte compiler was asked directly. On the server it renders the contents in full; on the client it emits the element EMPTY and never walks inside it. Interpolating the Polish sentence is therefore safe, a component inside it is safe, and the browser suite additionally asserts that the create screen with a preview loaded produces **zero console errors and zero page errors**.

The Playwright case for the no-script path asserts the notice's TEXT rather than its visibility, and the reason is written into the test: Playwright disables script EXECUTION, which does not flip the flag the HTML parser consults, so the element may stay text in that context. A real browser with scripting off in its settings renders it. Either way the sentence is in the document that was served, and the same case proves the thing that actually matters: the alt refusal fires with no client code involved at any point.
