## The Three Discoveries, In The Order They Bit

### 1. A default action and a named action cannot coexist, so the SAVE had to be named too

SvelteKit refuses to let one page carry both a `default` action and named ones, and the reason is exactly the shape of this screen: posting to a named action without a redirect leaves `?/dodajWiersz` in the URL, and the next default post would silently run the previous named action. So the plan's „default `zapisz` action" is a NAMED action `zapisz`, the form carries `action="?/zapisz"`, and only the add and remove buttons carry `formaction`. Nothing about the plan's intent changed; the mechanism did.

### 2. An action that SUCCEEDS resets the form, and that would have wiped the editor's work

This is the one line on each page that would have been a silent catastrophe if it were missing. `use:enhance`'s default behaviour for a **successful** result is to call the form element's own `reset()`, which restores every control to the value the document was **parsed** with. Adding a row is a success. So an editor who typed for ten minutes and then clicked „Dodaj wiersz" would have watched all ten minutes disappear, on a hydrated page only, with no error anywhere. Both screens call `update({ reset: false })`, and the reason is written above each one. The save and the refusal are unaffected either way: a refusal is not a success, and a save redirects.

### 3. Svelte computes `autofocus` ONCE, when the element is created, and never again

Caught by the browser suite rather than by reasoning, which is the point of having written the no-scripting case. `RegularElement.js` pushes `$.autofocus(node, value)` into the element's **init** block, so on a hydrated page the attribute is never added to an element that already existed and never removed from one that got it earlier. Two consequences, both real:

- the add button, which is never re-created, never received the attribute on the client, so focus after a removal fell to the top of the document. The no-scripting case caught this immediately (the server DOES render the attribute) and the hydrated case caught it a minute later;
- a query for `[autofocus]` would have found the row added a moment **ago** rather than the one added just now, because the older row still carries a stale one.

The fix is two honest mechanisms rather than one clever one: the server renders the attribute, which is the only thing that can work on a document nothing scripted, and the effect works from the request itself (the position for an item, the button element for a removal). A regression case adds two rows in a row and asserts focus lands in the SECOND one, which is the assertion that would have caught the stale-attribute version.

## What Was Built

**One repeatable-group component serves three lists**, and it authors not one visible string: the legend word, the note, both button labels and the announcement all arrive as props. Each item is a card with a numbered Polish legend, the remove button sits at the END of the item it removes (so the editor reads what is about to disappear before reaching the control that removes it), and the persistent note above the add button says that adding a row does not save. Reordering is absent in both directions and the file says so where somebody would otherwise add it.

**Row identity is position and nothing else.** Every control carries an indexed name (`wiersz[2].godziny`), the remove button carries the same position as its value, and `zbierzIndeksowane` collapses the submitted set into a dense ordered array. A hand-built request naming index 0 and index 5 yields two rows, not six and not an array with four holes in it. The index never selects a file, a record or an identity anywhere in the plan (T-04.1-34), and the removal is bounded against the set that ARRIVED, so out of range means „remove nothing" rather than „remove something else".

**A row that was emptied is still a row.** The collector treats a key that ARRIVED as presence, not a key that is non-empty. That distinction is what makes clearing both fields of a row a validation error the editor can act on, rather than a row that silently deletes itself on the next save.

**The head SHA travels in the form.** An add is a round trip, SvelteKit re-runs the load on the way back, and taking that fresh answer would have quietly moved the D-10 baseline forward: a colleague's commit landing while an editor was adding rows would then have been overwritten instead of refused. The value the browser carries is the state the form was BUILT from, which is what the check actually needs.

**Both validators are accountable to the committed files, not to themselves.** Neither content file has a guarding reader between it and the page, so the unit suite reads the real files, drives their real values through the validator as a form would, serializes with the real `serializujJson`, runs the result through this repository's own prettier, and compares the key set AND the key order. The staff counts come out as NUMBERS, asserted directly, and „sześć", „6 osób", „6.0", „-1" and „100" are all refused.

**The image island generalises, which is what Plan 07 built it for.** It is MOUNTED a second time, never rewritten: 4:3 instead of 16:9, the 4:3 ready sentence instead of the 16:9 one, and four index-scoped field names instead of four fixed ones. The browser suite measures the preview's real bounding box and asserts the ratio, so „it generalises" is a measurement rather than a claim.

**One save, one commit, whatever the session did.** The O nas action builds one file list (the JSON first, then one blob per pending picture) and makes exactly one call to the orchestrator, and the four list actions make none at all.

## Where The Plan And The Codebase Disagreed

**1. The formatting help does NOT sit under „Wprowadzenie".** The plan says „Wprowadzenie and Misja with the formatting help beneath each narrative field". `src/routes/o-nas/+page.svelte` renders `misja`, `kadra_opis` and `obiekt_opis` through the sanitizing inline renderer and prints `lead` as PLAIN TEXT. A help panel under Wprowadzenie would have promised an editor that two asterisks make bold there, and they would have published the asterisks. The help therefore sits under the three fields that really accept formatting. The UI-SPEC's own hint table already encodes this: only `misja` mentions formatting.

**2. A replacement keeps the name the picture already has, and only when the panel named it.** The plan's P-25 covers naming a new photo; it says nothing about replacing one. Deriving a fresh name on every replacement would write a new file, orphan the old one and move a URL for every wording fix, which P-21 already rejected for a cover. So a picture carrying a panel-generated name is overwritten in place. A picture the panel did NOT name is never overwritten, because a hand-placed file may be shared: both pictures in this repository today are rendered by a seeded aktualność as well, and overwriting one would change a photograph on a page nobody was editing.

**3. `uploads.ts` gained TWO exports, not one.** The plan says „Change nothing else in that module". Nothing existing was changed, and a second new export was added: `zdjecieONasDoUsuniecia`. The deletion rule has to agree with the naming rule about what „a name the panel generated" means, and Plan 07's finding is exactly what happens when those two live apart. Splitting them across two modules would have been the arrangement in which a prefix change breaks a deletion silently.

**4. The three cards without legends.** Contract 5 says a field group is a fieldset with a visible legend. The UI-SPEC's O nas copy table gives a legend for `wartosci` and for `obiekt_zdjecia` and for nothing else, so Wprowadzenie, Kadra and Obiekt render as plain cards. Inventing three legends would have put headings in the panel that the copy module never authored, which is exactly what `PolaWpisu.svelte` already declined to do on the aktualność screens.

## The Public Pages Had A Defect This Plan Would Have Exposed

**[Rule 1] `{#each dayPlan.rows as row (row.time)}` and `{#each onas.wartosci as wartosc (wartosc.tytul)}` were keyed by CONTENT.** That was harmless while the content was hand edited. From this plan on, a staff member can save two rows sharing a time range, or two wartość cards sharing a title, in about four seconds. Svelte **throws** on a keyed each block with two equal keys, and `node_modules/svelte/src/internal/client/errors.js` throws in production as well as in development. The prerender would have succeeded, the build would have succeeded, nothing would have warned, and the homepage and the O nas page would have broken the moment they hydrated.

Both were changed to key by position, which is unique by construction and renders identically. The alternative, refusing duplicates in the validator, was rejected: it would have invented an editorial rule the UI-SPEC does not have, and it would have left the same trap open for a hand edit. The full public suite (251 cases) confirms the pages render unchanged.
