## Test Infrastructure

| Property | Value |
|----------|-------|
| **Framework** | Playwright 1.62 + `@axe-core/playwright` 4.13 (E2E/a11y); `node:test` via `node --test` (unit) |
| **Config file** | `playwright.config.ts` (`testDir: 'tests'`, `webServer: npm run build && npm run preview:test`) |
| **Quick run command** | `npm run test:unit` (180 tests, ~140 ms) |
| **Full suite command** | `npm run check && npm run lint && npm run test:unit && npm run test` |
| **Estimated runtime** | ~140 ms unit; full suite dominated by the Playwright build+preview |

**Enforcement caveat (AG-3) — do not paper over this.** `npm run test:unit` runs in **no automated gate**: `npm run test` is Playwright-only (the `.unit.ts` suffix dodges Playwright's matcher) and pre-commit runs only `check` + `lint`. This phase writes the most security-sensitive code in the project. Every unit-tested invariant that matters for SC1/SC3 therefore needs a **second, enforced check** — a Playwright assertion, a build-output assertion, or a grep gate in the plan's acceptance criteria.

---

## Sampling Rate

- **After every task commit:** `npm run test:unit` + `npm run check`
- **After every plan wave:** `npm run check && npm run lint && npm run test:unit && npm run test`
- **Before `/gsd-verify-work`:** full suite green, all grep/build gates returning 0
- **Max feedback latency:** ~1 s for the unit sample; build-length for the wave sample

## Not Inferable From Unit Tests

These need held-out, property-based, or genuinely manual checks. A unit test written against the same mental model that wrote the code passes on all of them regardless of correctness.

| # | Behavior | Why not inferable | Required check |
|---|----------|-------------------|----------------|
| 1 | Enumeration-safety of the login (D-02) | A unit test proves the two response **bodies** match; the oracle is **timing** (allowlisted path awaits Resend, other does not) | Black-box on the deployed site: 10 requests each for a known and unknown address, compare response-time distributions |
| 2 | Atomicity of the two-file commit (D-07) | An injected-fetch test proves request **shape**, not that GitHub applied both blobs in one commit | Real commit against the real repo; `git show --stat <sha>` lists exactly two files |
| 3 | Conflict refusal on a stale SHA (D-10) | The interesting case is the **race** between the step-2 check and `update-ref`, which only `force: false` covers and no test reliably reproduces | Reasoning + a deliberate manual two-tab test |
| 4 | Prettier-cleanliness of emitted JSON (D-09) | Example-based tests would have passed the original Phase 3 defect | **Property-based**: generate across real field shapes (empty arrays, one-key objects, strings over `printWidth: 100`, embedded `\n`, Polish diacritics); assert `serializujJson(x) === prettier(serializujJson(x))` |
| 5 | Reader compatibility (SC5) | A hand-written fixture proves only that one fixture works | Property-based feed through `postFromEntry()` / `withMeta()`; assert non-null **and** no `console.warn` |
| 6 | The image actually renders after publish | The basename must land in the Vite glob; only a real build proves it | Playwright against the built preview: seeded upload renders a `<picture>`, not the tint fallback |
| 7 | Secrets reach the deployment | "Works locally with `--binding`, fails live" is the classic Pages-secret ordering bug | Live check after the secret-then-rebuild sequence |
