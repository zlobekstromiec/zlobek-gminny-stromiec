## Summary

I attacked the auth boundary, the write path and the upload path. Several things the
scope asked me to doubt turned out to be genuinely closed, and I will say so plainly
rather than manufacture findings:

- **`static/admin/` is gone.** `git diff --name-status` shows all eleven files under it
  deleted and the directory does not exist. Nothing in `static/` can shadow an `/admin`
  route. `src/routes/admin/+layout.ts` opts the subtree out of prerendering, so no
  snapshot ships either.
- **The gate is genuinely one gate.** `handle()` runs before routing, so `+server.ts`
  endpoints, `__data.json` requests and form actions are all covered, and the non-GET
  branch returns a `Response` rather than throwing so a POST cannot be swallowed.
- **The allowlist is re-checked per request** (`hooks.server.ts:60`) and again at the
  moment a session is minted (`logowanie/+page.server.ts:259`). Removing an address does
  log that person out.
- **Path traversal is closed by construction, everywhere I could reach.** Route
  parameters are only ever used to *look up* an entry among slugs the readers derived
  from real on-disk filenames; every written path is rebuilt from the entry
  (`sciezkaWpisu`, `sciezkaOkladki`, `sciezkaDokumentu`, `sciezkaTresciDokumentu`). The
  one client-supplied basename (`POLE_OBRAZ`) goes through the `WZORZEC_NAZWY` allowlist.
  `sciezkaZPubliczej` rejects `/`, `\` and `..`.
- **The commit path is atomic and cannot both write and delete one path.** The
  `usunOkladke` expression at `walidacja/aktualnosci.ts:297` and the `wMiejscu` branch at
  `walidacja/o-nas.ts:318` really do enforce the P-21 exclusion; the base64 charset is
  re-checked in `commit.ts:131-135` before the concatenated blob body is built, so the
  splice in `cialoBloba` is safe.
- **No key material reaches a log, message or commit.** `console.warn` appears six times,
  all in `kod.ts`, all fixed strings naming a binding. `komunikatCommita` scrubs twice and
  asserts. No `@html` anywhere in the panel except the committed instrukcja, which goes
  through a hardened `Marked` renderer.
- **Uploads are validated server side**, not only in the island: `walidujWpis`,
  `walidujONas` and `walidujDokument` all re-read the data URL, the type allowlist and the
  alt requirement from the `FormData`.

What I found is one hole in the login boundary that the phase's own threat register
believes is covered when it is not, plus five quality/robustness defects.

## Critical Issues

### CR-01: The one-time code exchange has no rate limit, and the attempt cap it relies on instead cannot be enforced reliably on KV

**File:** `src/routes/admin/logowanie/+page.server.ts:174-199`, `src/lib/server/admin/kod.ts:264-276`

**Issue:**
`kod.ts:22-24` states the security model explicitly: *"Six digits are defensible only
because of MAKS_PROB below: the hard attempt cap, not the length, is what makes the 10^6
space unguessable."* `04.1-02-PLAN.md:219` claims the mitigation is *"Hard cap of five
attempts that BURNS the code, 15-minute TTL, **plus the per-client hourly limiter**"*.

That last clause is not true. `podLimitemKodu` is called only in the `wyslij` action
(line 134). The `zaloguj` action calls `sprawdzKod` directly at line 199 with no limiter
of any kind, so an unauthenticated client may POST code guesses to `?/zaloguj` at
whatever rate it can generate them. The 5-attempt cap is therefore the *only* control,
and it is implemented as a non-atomic read-modify-write against KV:

```ts
const wpis = czytajWpis(await kv.get(klucz));   // read
...
const proby = wpis.proby + 1;                    // modify
if (proby >= MAKS_PROB) { await kv.delete(klucz); ... }
await kv.put(klucz, JSON.stringify({ ...wpis, proby }), ...);  // write
```

Three independent reasons this does not bound guesses at five:

1. **Concurrency.** N guesses issued in parallel all read `proby: 0` and all write
   `proby: 1`. One burst of N requests yields N guesses and advances the counter by one.
   Five bursts therefore yield 5N guesses, not 5.
2. **Eventual consistency.** KV propagates a write to other locations in up to 60
   seconds, so guesses arriving at different Cloudflare PoPs read a stale count even when
   they are strictly sequential in wall-clock time.
3. **Read caching.** `kv.get` serves from the colo cache with a default `cacheTtl` of 60
   seconds, and the documented minimum for that option is also 60 seconds, so there is no
   way to make this read fresh enough for a counter.

**Concrete failure enabled:** an attacker who knows a staff address (a `@ugstromiec.pl`
address is guessable for a gmina unit) requests a code — the real editor receives it and
may well ignore it — then floods `?/zaloguj`. A few thousand concurrent guesses per burst
against a 10^6 space gives a materially non-trivial hit rate per code, and the site-wide
budget still allows 20 codes a day. A hit is a full editor session: write access to a
public repository, which on the next Pages build is arbitrary content on a public body's
website. The same defect also makes the single-use burn on success replayable across PoPs
for up to a minute.

Note that the two enforced tests cannot see this: the unit case and the Playwright case
both drive the cap *sequentially from one client*, which is exactly the access pattern
the counter handles correctly.

**Fix:** give the exchange its own per-client budget, so correctness no longer depends on
the KV counter being atomic. Minimal change, using the machinery that already exists:

```ts
// src/lib/server/admin/kod.ts
/** Guesses per client per hour, on a bucket of their own so a flood of wrong codes
 *  cannot consume the budget for requesting a new one. */
export const LIMIT_PROB = 10;

export async function podLimitemProby(
	kv: KVNamespace | undefined,
	ip: string,
	sol: string,
	teraz: number,
	limit: number = LIMIT_PROB,
	limitDobowy: number = LIMIT_KODOW_DOBOWY
): Promise<boolean> {
	return podLimitem(kv, 'admin-proba', ip, sol, limit, limitDobowy, teraz, PREFIKS_DOBOWY_PANELU);
}
```

```ts
// src/routes/admin/logowanie/+page.server.ts, in `zaloguj`, before sprawdzKod
if (!(await podLimitemProby(env?.FORMS_KV, event.getClientAddress(), sol, teraz, limit))) {
	return fail(429, {
		krok: 2,
		adres,
		panelNaglowek: KOPIA_LOGOWANIE.limitNaglowek,
		panelTresc: KOPIA_LOGOWANIE.limitTresc
	} satisfies WynikLogowania);
}
```

This limiter keeps `ratelimit.ts`'s documented fail-open degrade, which is acceptable here
only because it is now defence in depth *alongside* the cap rather than a replacement for
it; if you prefer, invert it to fail closed for this one call site. Either way, update
`04.1-02-PLAN.md:219` so the register stops claiming a limiter that was never wired up.

**Outcome: FIXED**, commit `be11839`. Three judgement calls made while applying it, all
deliberate departures from the suggestion above:

1. **It fails CLOSED, not open.** `ratelimit.ts`'s fail-open degrade is right for the
   public contact form, where refusing a parent costs an enquiry stored nowhere. It is
   wrong on a credential-guessing endpoint: on a KV outage, failing open removes the only
   rate limit in front of a 10^6 space. It costs an editor nothing, because `sprawdzKod`
   one function down already refuses the login on the same outage („operacja KV nieudana,
   logowanie odrzucone"), so nobody logs in during a KV failure either way and the only
   thing this direction changes is that nobody guesses during one either. The direction is
   chosen at the call site through a new trailing `wynikPrzyAwarii` parameter on
   `podLimitem`, defaulting to `true`, so every existing caller is byte-identical.
2. **The guesses get their own DAILY bucket too** (`PREFIKS_DOBOWY_PROB`), not only their
   own hourly one. The snippet above passes `LIMIT_KODOW_DOBOWY` on the panel's shared
   daily prefix, which would mean an editor who mistyped their code could no longer ask
   for a new one, and 20 guesses from anyone would refuse every code request site-wide for
   the rest of the UTC day. Guesses also send no mail, so they have no business inside a
   ceiling that exists to protect a send budget. `LIMIT_PROB = 10` per client per hour;
   `LIMIT_PROB_DOBOWY = 500` site-wide, documented in the source as a runaway guard rather
   than as the control, because every site-wide ceiling is also an availability lever.
3. **`04.1-02-PLAN.md:219` was not edited**, for the reason given under „Fix outcome".

Coverage added, and the shape of it is the point: the two enforced tests could not see
this defect because both drove the cap sequentially from one client, which is exactly the
pattern the broken counter handles correctly. The new cases are a CONCURRENT burst against
`sprawdzKod` (twenty guesses fired without awaiting in between: all twenty are admitted
and the counter advances by one, asserted rather than described, so the day the counter
becomes atomic the assertion goes red); its paired sequential positive control, so the
burst case cannot pass on a module with no cap at all; the budget's own behaviour
including its fail-closed direction, its separate buckets and a positive control that it
admits a first guess; and a structural case in `tests/admin-auth.spec.ts` proving the call
sits inside `zaloguj` and ahead of `sprawdzKod`, verified by mutation (deleting the call
turns it red).

**Residual weakness, stated rather than implied away:** the budget is keyed on the client
address. An attacker spread across many addresses is still bounded only per address, up to
the deliberately loose site-wide ceiling. The attempt cap is still not strict and cannot be
made strict on KV. This narrows the exposure by orders of magnitude; it does not close it.

## Warnings

### WR-01: The e-mail address is never case-normalised, so one editor is several identities

**File:** `src/routes/admin/logowanie/+page.server.ts:104` and `:176`

**Issue:** `bezpiecznyEmail` (`src/lib/server/forms/sanitize.ts:53-60`) trims but does not
lowercase. `naLiscie` (`allowlist.ts:43-50`) lowercases both sides, so
`Anna@ugstromiec.pl` and `anna@ugstromiec.pl` are the same allowlisted person. But
`kluczKodu` (`kod.ts:117`) and `skrotKodu` (`kod.ts:126`) hash the raw string, and the
session payload stores the raw string (`sesja.ts:117`).

**Concrete failure enabled:** each case variant of one address gets its own KV entry, its
own live code and its own independent 5-attempt budget, all delivered to the same real
inbox. That multiplies both the number of simultaneously valid codes for one person and
the guess budget against them — it amplifies CR-01 and it is worth fixing even after
CR-01 is fixed. It also means two sessions for the same human carry different `adres`
values, so an operator reasoning about revocation has two things to think about instead
of one.

**Fix:** normalise once, at the boundary, in both actions:

```ts
const surowyAdres = bezpiecznyEmail(dane.get('adres'));
const adres = surowyAdres === null ? null : surowyAdres.toLowerCase();
```

`uchwytZAdresu` already lowercases, so commit messages are unaffected.

**Outcome: DEFERRED**, no change made. Still open.

### WR-02: An image payload is never inspected, so a bad upload commits cleanly and then breaks the site build

**File:** `src/lib/server/admin/obraz.ts:61-66`; consumers at `src/routes/admin/aktualnosci/nowy/+page.server.ts:120-132`, `src/routes/admin/aktualnosci/[slug]/+page.server.ts:149-158`, `src/routes/admin/o-nas/+page.server.ts:229-236`

**Issue:** `base64ZDataUrl` checks the declared media type, the length and the base64
charset. It deliberately never decodes. That is the right call for CPU budget, but the
bytes land in `src/lib/assets/uploads/`, which `uploads.ts:90` and the three public
consumers glob with `query: { enhanced: true }` — i.e. every file there is decoded by
`@sveltejs/enhanced-img` **at build time**.

**Concrete failure enabled:** a payload that is valid base64 and correctly labelled
`image/jpeg` but is not a decodable image (a truncated data URL from a flaky mobile
upload, or a hand-built request) is accepted, committed, and reported to the editor as
„Zapisano". The next Cloudflare Pages build then fails on the image transform, so the
whole public site stops deploying — including any subsequent fix an editor tries to make
through the panel, because the panel's only write path is a commit that triggers that same
build. Recovery requires someone with git access, which is precisely the person this
project assumes will not be around.

**Fix:** check the magic bytes of the first few decoded bytes. It costs one `atob` over a
16-character slice, not the whole payload:

```ts
const SYGNATURY: readonly (readonly number[])[] = [
	[0xff, 0xd8, 0xff], // jpeg
	[0x89, 0x50, 0x4e, 0x47] // png
];

/** True when the payload really begins as one of the accepted formats. WEBP is
 *  `RIFF....WEBP`, so it is checked on bytes 0-3 and 8-11. */
function znanaSygnatura(base64: string): boolean {
	const naglowek = atob(base64.slice(0, 24));
	const bajty = [...naglowek].map((z) => z.charCodeAt(0));
	if (SYGNATURY.some((s) => s.every((b, i) => bajty[i] === b))) return true;
	return naglowek.startsWith('RIFF') && naglowek.slice(8, 12) === 'WEBP';
}
```

Refuse with the existing `KOPIA_WALIDACJA.zdjecieZlyTyp` sentence when it returns false.

**Outcome: FIXED**, commit `f94c7df`. The check reads 24 characters of the payload (18
bytes, enough to reach WEBP's second marker), decodes them with one `atob`, and compares
against the JPEG, PNG and WEBP openings. A slice that is not whole base64 quadruples, and
a payload too short to hold a signature, both fall through to a refusal rather than
throwing, which is asserted over every payload length the charset pattern admits: an
escaped throw here would be a 500 instead of a Polish sentence on the upload screen. The
refusal reuses `KOPIA_WALIDACJA.zdjecieZlyTyp`, so no new copy was added.

Coverage: valid base64 that is correctly labelled and is not an image, driven through all
three declared types (plain text, a PDF, the old meaningless payload this test file used
to share, a GIF whose signature is deliberately not in the allowlist, and `RIFF` without
the `WEBP` marker, which is what a WAV file looks like), plus a positive control per
accepted format so the check cannot pass by refusing everything. The old fixtures in
`tests/admin-obraz.unit.ts` and `tests/admin-walidacja-aktualnosci.unit.ts` carried
meaningless bytes and were replaced with real headers.

**Stated in the tests rather than implied:** the check is a UNION of the three signatures.
It does not cross-check the bytes against the declared media type, and it reads a header
rather than decoding the file, so a PNG labelled `image/jpeg` passes and so does a file
truncated just after its header. Both of those still carry a decodable opening, which is
what the build needs. The class this closes is „these bytes are not an image at all", not
„this image is undamaged".

### WR-03: No `Cache-Control` on panel responses, contradicting the comment that claims there is

**File:** `src/routes/admin/pomoc/instrukcja/+server.ts:29-31`, `src/hooks.server.ts:39-83`, `_headers:15-20`

**Issue:** the instrukcja endpoint sets `'cache-control': 'no-store'` and its comment says
*"No store, like every panel response."* No other panel response sets it. A repository-wide
grep finds `cache-control` in exactly that one file, `_headers` has no `/admin` block (by
deliberate design, per its lines 11-14), and `hooks.server.ts` never calls `setHeaders`.

**Concrete failure enabled:** panel HTML — which carries content, the editor handle and,
on the login screen, the editor's own e-mail address in a hidden field — is left to
browser heuristic caching and to the back/forward cache. After „Wyloguj" on a shared
żłobek computer, the browser Back button re-displays the previous panel screen with all of
it intact. The session cookie is correctly cleared, so no *new* request succeeds, but the
rendered data is still on screen.

**Fix:** one line in the gate, where the `/admin` branch is already isolated:

```ts
// src/hooks.server.ts, just before the final `return resolve(event);`
event.setHeaders({ 'cache-control': 'no-store' });
```

and set it on the refusal responses too, or drop the misleading half of the instrukcja
comment if the risk is judged acceptable.

**Outcome: DEFERRED**, no change made. Still open.

### WR-04: The installation-token response is cast, not validated, at a credential boundary

**File:** `src/lib/server/admin/github.ts:194-196`

**Issue:**

```ts
const dane = (await odpowiedz.json()) as { token: string; expires_at: string };
pamiecTokenu = { token: dane.token, wygasa: Date.parse(dane.expires_at) };
return dane.token;
```

Nothing checks either member. `zapis.ts` and `commit.ts` guard every other external
boundary in this phase; this one is the credential.

**Concrete failure enabled:** a 200 response with an unexpected body (a GitHub incident, a
proxy, a future API change) yields `Bearer undefined` on all six subsequent Git Data calls
of the save — the editor sees the generic failure panel with no way to distinguish it from
a network problem — and `Date.parse(undefined)` is `NaN`, so `pamiecTokenu.wygasa > teraz +
MARGINES_MS` is always false and the module-scope cache that this file exists for is
silently disabled for the isolate's lifetime, costing an extra signature and round trip on
every save thereafter.

**Fix:**

```ts
const dane = (await odpowiedz.json()) as { token?: unknown; expires_at?: unknown };
const wygasa = typeof dane.expires_at === 'string' ? Date.parse(dane.expires_at) : NaN;
if (typeof dane.token !== 'string' || dane.token.length === 0 || !Number.isFinite(wygasa)) {
	throw new Error('github: token instalacji nieczytelna odpowiedz');
}
pamiecTokenu = { token: dane.token, wygasa };
return dane.token;
```

**Outcome: DEFERRED**, no change made. Still open.

### WR-05: The nabór screen retypes the form-field names every other screen imports

**File:** `src/routes/admin/nabor/+page.server.ts:65`, `:91`, `:128`

**Issue:** every other editor screen imports `POLE_SHA` and `ZNACZNIK_ZAPISANO` from
`$lib/pola-wpisu` / `$lib/pola-strony` / `$lib/pola-dokumentu`. This one writes

string literals. `src/routes/admin/nabor/+page.svelte:132` renders
`<input type="hidden" name="sha" ...>`, also a literal. The values happen to match

**Concrete failure enabled:** the day someone renames the constant — which the codebase
treats as a safe refactor everywhere else — this screen keeps posting `sha` and keeps
reading `sha`, or the two halves drift apart and `oczekiwanySha` becomes `undefined`.
`zapiszAtomowo` documents `undefined` as *skip the check*, so the D-10 stale-save guard
would be silently switched off on the one screen that flips the public recruitment banner,
with no test failing and no message to the editor. This is exactly the "silently lost edit
reported as saved" class the phase spent Plan 05 closing.

**Fix:** import the constants in both the server file and the page, as the other five
screens do.

**Outcome: DEFERRED**, no change made. Still open.

### IN-02: Prototype keys are reachable through the section-name lookup

**File:** `src/routes/admin/+layout.server.ts:34`

**Issue:** `SEKCJE[segment] ?? 'Panel redakcyjny'` indexes a plain object literal with a

**Fix:** `const SEKCJE: Record<string, string> = Object.assign(Object.create(null), { ... })`,

### IN-03: The photo group cap allows a request nobody budgeted

**File:** `src/lib/pola-strony.ts:96` with `src/lib/server/admin/obraz.ts:38`

**Issue:** `MAKS_ELEMENTOW = 30` and `MAKS_BASE64 = 1_400_000`, so the o nas save accepts a

**Fix:** cap the photo group specifically (a `maks` argument to `zbierzIndeksowane` for

scope as a performance matter; noted because the failure is a 500 rather than a message.
