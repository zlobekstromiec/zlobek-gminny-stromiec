  <action>
Two files.

**`src/lib/components/Lightbox.svelte` (new).** Transposed from `MobileNav.svelte` line for
line where the behaviour is the same. Four properties are load-bearing and easy to lose, and
each has a named consequence:

1. **The focus restore lives in the effect's CLEANUP, not in a click handler.** Doing it in a
   handler means Escape and the scrim click each need their own restore and one of them will
   be forgotten.
2. **The dialog element carries the dialog role, `aria-modal` true, `tabindex="-1"` and the
   keydown handler**, and the handler is on the DIALOG, never on the window.
3. **The transition duration comes from a function**, so reduced motion is honoured in JS, and
   a component-scoped reduced-motion CSS block neutralises the transition a second time. Both
   layers, exactly as the precedent does.
4. **The scrim needs the two `svelte-ignore` comments verbatim**, with the same explanatory
   comment above them stating that keyboard users dismiss via the close button or Escape so the
   static element carries no keyboard handler by design. Without them `npm run check` fails at
   pre-commit on the click-events-need-key-events and static-element-interaction rules.

Deltas from the precedent, all from Contract 2:
- The trigger is the tile's existing `<a href>`, not a button. The island intercepts only a
  plain primary click with no modifier key; a modifier or a middle click falls through so
  opening the image in a new tab keeps working. Keyboard Enter and Space on the link open the
  dialog. There is no conditional markup and no layout change on hydration.
- `aria-labelledby` points at the caption element inside the dialog rather than at a literal
  label.
- The motion is an opacity fade only. Nothing translates, nothing scales, there is no crossfade
  and no zoom from the thumbnail.
- Contents in DOM order: close button, image, caption as a heading, alt description line. The
  close button is the first focusable element, sits inside the panel's corner and never floats
  on the scrim alone, because a control whose only backing is a translucent overlay has no
  guaranteed contrast against the photo behind it.
- The scrim value is built from the existing ink triple at the contract's opacity, matching how
  the shadow tokens already express it. No new hue and no new token.
- No navigation between photos. No arrows, no swipe, no counter. This is a recorded deferral,
  written here so an executor does not invent it: a previous and next pair is a second
  focus-order problem, a second keyboard contract and a second set of Polish strings, for a
  twelve-photo set a visitor can close and reopen.
- No preloading, no separate fetch, no spinner, no progress bar and no skeleton. The dialog
  renders the same responsive source the tile already has, so it normally paints from cache. A
  spinner is the easiest reduced-motion violation to ship by accident.
- No error state. There is no runtime fetch, and an entry whose file is missing was already
  dropped by the build-time reader, so the dialog can never open onto nothing.
- Author no visible string in this component beyond what the contract specifies; the close
  button's accessible name, the caption and the description all come from props or from the
  copy the page already holds.

**`src/routes/o-nas/+page.svelte`.** Mount the island per tile, passing the picture, the
caption and the alt. The enhanced image element stays in the PAGE and is passed in as a
snippet, so the island carries no image-processing concern. The header comment was already

change.

**Do not widen the CSP.** The island is same-origin and inline scripts already carry the
per-response nonce. Nothing in `svelte.config.js` changes.
