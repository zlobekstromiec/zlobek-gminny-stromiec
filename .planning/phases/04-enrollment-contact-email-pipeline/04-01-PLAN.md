## Phase Goal

**As a** rodzic (parent), **I want to** read enrollment information, download the wnioski, and send an enrollment or contact message from the website, **so that** I can reach the żłobek and start the enrollment process without a visit, knowing my data is handled lawfully and never stored.

> Phase-goal note: the ROADMAP `**Goal:**` line for Phase 4 is written as a capability sentence ("Parents can find enrollment information, download the forms, and submit enrollment and contact requests that are safely emailed to the żłobek") rather than in the bolded three-slot user-story form. The story above restates that same goal, slot for slot, without adding scope.

## MVP Slice (this plan)

**Slice A (Kontakt), plan 1 of 3.** After this plan a real HTTP client can POST a contact message to `/api/kontakt` running on the real Cloudflare runtime and get a delivered e-mail (dry-run seam in local test runs), with every rejection path returning a truthful status code. This is the first working end-to-end path of the phase: browser-visible UI lands in Plans 03 and 04 on top of an already-proven pipeline.

<objective>
Build the shared server-side form pipeline and the first endpoint that uses it: input sanitizing, validation, server-side Turnstile verification, a KV rate-limit counter, and a Resend send with hard-coded sender and recipient (CONTACT-03, FORM-01, FORM-02).

Purpose: this is the security and compliance boundary of the whole phase. Every later plan hangs UI on it, so it is built first, proven by unit tests over pure functions and by endpoint tests against the real Cloudflare runtime.
Output: a working POST /api/kontakt endpoint, a reusable src/lib/server/forms/ module, the platform bindings and CSP that the widget needs, and two green test files.
