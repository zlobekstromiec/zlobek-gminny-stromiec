<objective>
Land the high-contrast theme's token flip and the site-chrome half of its component override register.

Purpose: D-08 makes high contrast yellow on black, the convention a Polish visitor recognises from
other public-body sites. D-09 says overriding backgrounds wholesale is what makes that tractable. The
UI-SPEC is explicit that a token flip ALONE reaches roughly 70 percent of the surface and produces a
demonstrably broken mode: a white-on-white footer, an invisible nav chip label and a white tick on a
yellow checkbox. Its own ordering note therefore permits Layer 1 to land only behind an attribute the
widget does not yet expose. That is exactly what this plan does, and plans 05 and 06 finish the
register before plan 07 hands the control to a visitor.

Output: the flip table in `app.css`, and the override blocks for TopBar, Header, Footer, SkipLink,
Cta, Wave and MobileNav.
</objective>

  <action>
    Add ONE block to `src/app.css`, after `@theme` and after the text-scale `:root` block from plan 03,
    keyed on the contrast attribute.

    Declare the three high-contrast values as their own custom properties so they can never leak into
    the accessible tier and never generate a Tailwind utility. Exactly three, and the reason is
    arithmetic rather than taste: the danger token on black measures 3.25 to 1 and fails AA outright,
    and a focus ring must be distinguishable from the border it surrounds, so two roles cannot be
    carried by the text value. Note in the comment that the one weak pair among the three measures
    1.07 to 1, which is why the third value appears only where a black surface or the ring's own 2px
    black offset separates it from the text value.

    Then flip all 23 `--color-*` tokens per the UI-SPEC table. Every token in `@theme` appears; none
    is omitted. Four rows carry reasoning that must survive into the comment because a later reader
    will otherwise "fix" them: the muted tier collapses into the text value ON PURPOSE, because
    lightening or darkening text toward the background is the exact thing a high-contrast user is
    escaping; the brand-blue token flips for its TEXT role only, and its FILL role is handled per site
    in Layer 2 because one token cannot be both a foreground and a background in an inverted theme;
    the subtle-border token becomes a real border because the mode leaves no tint to separate blocks;
    and the expressive and tint families flip to the background so decorative blobs vanish rather than
    becoming yellow shapes competing with text.

    Do NOT flip the font or radius families. The mode changes colour and edge treatment, never type or
    shape.

    Add two explicit non-rules, each with its reason, so a reviewer sees they were decided rather than
    overlooked: `prefers-contrast: more` is NOT wired to this theme, because a visitor whose operating
    system asks for more contrast already gets a site that meets AA and silently repainting it would
    be a surprise nobody requested; and `forced-colors` is NOT overridden anywhere, no
    `forced-color-adjust` is added, so if a visitor is in a system high-contrast mode AND turns this
    on, the system palette wins, which is correct.
  </action>
